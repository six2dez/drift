<objective>
Replace Gemini and Codex's shared-wrapper registration with the validated Node executable plus
arguments plus an explicit environment, on every platform — and delete the POSIX shell wrapper the
old shape existed to carry.

Those two halves are ONE commit, not two: the wrapper-writing functions lose their last caller here,
and the repo's `noUnusedLocals` and zero-warning lint settings turn an uncalled module-scope function
into a hard build failure. A tree that registers the new way but still declares the old renderer does
not compile, so SC-7's deletion checklist is this plan's, not a later cleanup's.

Purpose: PRV-03 and SC-3, plus the fail-closed half of PRV-05. Output: a pure registration-payload
builder with its tests, both registration spawns routed through 07-01's plan, and four symbols plus
the last permission-bit spawn gone from the backend entry module.
</objective>

  <name>Checkpoint: where the Caido session token rests for Codex after the wrapper is deleted</name>
  <decision>Where the Caido session token lives for Codex, now that the POSIX wrapper is being deleted</decision>
  <context>
    This changes where a live credential rests on the user's disk, and it deviates from a roadmap
    success criterion, so it is not the planner's to settle.

    Today the token never enters `~/.codex/config.toml`. Drift registers a wrapper SCRIPT path with
    the CLI, and the token lives inside that script in the swept, owner-only temp directory. SC-7
    deletes that wrapper. After this plan the registration must carry the environment itself, so the
    token moves INTO the CLI's own persistent configuration file — outside the temp root the orphan
    sweep has ever looked at, and outside the accepted per-user temp ACL baseline. Any backup,
    profile-sync or dotfile-repo that covers the home directory now covers the credential.

    ROADMAP SC-3 authorises two shapes for Codex: a variable reference, or a token-file indirection.
    Research established that the first is IMPOSSIBLE — that CLI performs no expansion anywhere on its
    read path, so the reference text would be handed to the MCP server verbatim as the token, always,
    not merely when unset. That leaves the literal, which SC-3 does not name, or the token-file
    indirection, which research recommends against for this phase. The gap is real and the user should
    close it, the same way SC-2 was amended earlier in this planning run.

    Reversibility: one-way in the disclosure sense. Removing the entry later deletes the bytes from the
    live file; it does not recall them from a backup taken while they were there.
  </context>
  <options>
    <option id="literal-plus-guarantees">
      <name>Literal token in the CLI config, with a guaranteed dual removal and a security log line</name>
      <pros>Works today with no new mechanism. Matches what 05-D-10 already blessed for the other CLI's config document. Keeps this phase to one new pure module, which the research's own don't-hand-roll table names as the signal that scope is right. The exposure window is bounded by 07-04's unconditional startup sweep plus the removal on cleanup, and a failed removal becomes a logged security event with a remediation command the user can paste.</pros>
      <cons>A live Caido session token rests in a home-directory file between sessions, outside the swept temp root, and survives a crash until the next Drift start. Any home-directory backup captures it. This is the phase's highest-severity accepted residual.</cons>
    </option>
    <option id="token-file-indirection">
      <name>Build the token-file indirection SC-3 names</name>
      <pros>No credential bytes in the CLI config at all. Enables token rotation without re-registration, which is the only reason to prefer a file over a value. Closes the residual rather than bounding it.</pros>
      <cons>A new cross-provider mechanism in a phase whose other half is deleting mechanisms: a new environment key, a read with its own failure handling in the MCP server, a decision about frozen-at-start versus per-call re-reading (only the per-call form buys rotation), and a matching write, lifetime and cleanup in the backend. Roughly one additional task plus its tests, and it is precisely what 05-D-10 declined to build for the same reason.</cons>
    </option>
    <option id="no-codex-registration">
      <name>Do not register Codex at all until the indirection exists</name>
      <pros>Zero credential exposure. Honest, and the capability surface from 07-02 can state it precisely.</pros>
      <cons>Regresses a provider that works on macOS and Linux today, which is a direct CMP-01 violation — the milestone invariant that every phase preserves existing POSIX behaviour. Rejected on those grounds unless the user overrides.</cons>
    </option>
  </options>
