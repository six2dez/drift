## Planner decisions recorded for this plan

These close three of the five open questions 06-RESEARCH left to the planner. Each is a stated
rationale, not a deferral.

- **The `.cmd` spawn hazard this plan creates is closed at the spawn HELPER, not by filtering the
  candidate list. Option taken: wrap `spawn` in `spawnAndWait` in try/catch (T-06-03A).**
  This plan is the first to put `.cmd` and `.bat` candidates in front of a loop that SPAWNS them:
  `getNodeExecutable` (`index.ts:2482`) runs `await spawnAndWait(candidate, ["--version"])` on
  every candidate that passes `fileExists`, and `spawnAndWait` (`index.ts:2396`) calls `spawn()` on
  the first line of a `new Promise` executor with no try/catch. Phase 3's P1-CMD measured a direct
  `.cmd` spawn throwing `EINVAL` SYNCHRONOUSLY under Node's CVE-2024-27980 guard; a synchronous
  throw inside a Promise executor REJECTS the promise, so `proc.on("error")` never fires and
  CLAUDE.md's documented *"spawnAndWait always resolves, never rejects"* invariant breaks. The
  rejection then travels `resolveWithCache` → `requireNodeExecutable` → `startMcpServer` with no
  catch on the path — the exact unhandled-RPC-rejection failure the comment at `index.ts:2447-2461`
  already treats as a defect worth defending against.
  It was previously unreachable only because Windows does not set the POSIX home variable, so the
  home-derived candidate list was empty there; D-08 (plan 06-05) removes that accident, and T-06-06's
  Volta-image-before-shim ordering mitigates exactly one version manager while scoop's `node.cmd`
  shim, nvm4w and D-11's extension ladder across all nine locations leave `.cmd` reachable at many
  others.
  **The rejected alternative was skipping non-`.exe` candidates in the win32 node-validation loop.**
  Three reasons it loses. First, blast radius, counted rather than recalled
  (`grep -n 'spawnAndWait' packages/backend/src/index.ts`): `spawnAndWait` has SIX call sites —
  `:1372`, `:1387`, `:2482`, `:2555`, `:2556`, `:2643`. Exactly THREE of them — the
  `mcp remove`/`mcp add` pair at `:2555`/`:2556` and the `mcp remove` at `:2643` — receive a
  RESOLVED PROVIDER CLI path (`cliBinary`, `storedPath`), which on Windows after this phase can
  itself be a `.cmd`. All three sit OUTSIDE the node-validation loop, so a filter in that loop
  leaves every one of them crashing. Two further sites are not provider-CLI paths and are counted
  separately, not folded into the three: `:1372` receives the literal `"chmod"`, and `:1387`
  receives `spec.command`, which the comment above `validateCaidoAuth` states is `node` for
  `mcp-server.mjs`. `:1387` still carries INDEPENDENT `.cmd` exposure once D-11's extension ladder
  can resolve `node` to a Volta or fnm `node.cmd` shim — a node-shim risk, not a provider-CLI one —
  which is a second reason the guard belongs to the helper rather than to one loop. `:2482` is the
  node-validation loop itself, the site the rejected filter would have covered. Second, Phase 7 consequence: the filter is scaffolding Phase 7 would have to find and
  remove, and until it did, a Volta- or scoop-only Windows user would be told Node is missing when
  it is installed — a scope reduction wearing a safety label. The try/catch is not scaffolding; it
  is a correctness fix to a helper whose documented contract is currently false, and Phase 7 keeps
  it unchanged. Third, honesty: the filter would encode a claim about which extensions are
  spawnable, which is PRV-02's claim to make. The try/catch encodes only that a failed spawn is a
  failed candidate, which is true under every answer Phase 7 reaches.
  **Hand-off to Phase 7, recorded rather than assumed:** after T-06-03A a `.cmd` candidate that
  Windows refuses resolves as `{ code: 1 }`, so the validation loop treats it as "not a working
  executable" and walks to the next candidate. That is graceful degradation, NOT launchability.
  Making a `.cmd` actually launch remains PRV-02 in Phase 7, and the task plants a greppable
  `PRV-02` marker at the guard so that phase can find the seam by search.

- **Q3 — version-walk depth: keep the walk, bound the win32 emission to the newest 3 version
  directories per root. POSIX stays unbounded and unchanged.**
  Reason: `stat` is slowest on Windows and D-09 already grows the location count, so an unbounded
  walk multiplies the cost on exactly the platform that can least afford it. The walk is kept
  rather than dropped because a broken `PATH` is the case it exists for — research row P-06 shows
  the nvm-windows symlink directory is added to `PATH` by the installer, so `where.exe` already
  finds an nvm-managed Node when `PATH` is intact, which makes the walk a fallback rather than the
  primary route. Bounding to 3 is a COST bound chosen by the planner, not a measurement, and the
  code comment must say so. The existing lexical reverse sort is NOT semver-correct (a v9 entry
  sorts after a v10 entry); that is pre-existing POSIX behaviour, CMP-01 says leave it alone there,
  and it is mirrored on win32 for symmetry rather than fixed — fixing it is not RES-01's job and
  would be a silent behaviour change on macOS/Linux.
- **Q4 — the provider-adjacent node sibling: keep `path.dirname` host-flavoured, move it into the
  thin impure caller, and pass the resulting DIRECTORY into the pure builder.**
  Reason: `command-resolution.test.ts:98-107` records that this derivation is host-flavoured BY
  DESIGN and cites the real `windows-latest` red that taught it — on a real Windows host the
  module is win32-flavoured and the derivation is correct. But leaving the derivation INSIDE the
  pure builder would make its win32 row unassertable on the Linux runner, which is the exact hazard
  D-05 exists to kill. Splitting it resolves both: the host-flavoured `dirname` stays where its
  recorded rationale applies, and the pure builder receives literal directories it can spell for
  the target platform. D-05's sweep names "every `path.join`" and does not name `dirname`; this
  records the exception in code so a later reader does not "finish the sweep".
  The sibling also gains the extension ladder on win32 — a bare `node` beside a `claude.cmd` is
  not a Windows executable name.
- **Q5 — `%ProgramFiles(x86)%\nodejs`: KEEP, tagged as an assumption in the code comment.**
  Reason: the variable is standard and the row costs one `stat` that PERF-03's cache absorbs, but
  no first-party statement ties a current Node MSI to it, so it cannot be tagged verified. The
  justification that keeps it alive is WOW64 bitness: on 64-bit Windows a 32-bit process sees
  `%ProgramFiles%` pointing at the x86 tree while a 64-bit process does not, so reading BOTH
  variables is the arm that survives whichever bitness Caido's backend host turns out to be. That
  reasoning goes in the comment beside the row.

**Rows DROPPED under D-12 and recorded as explicit non-claims in the code** (a later reader must
find the reason beside the table, not have to re-derive it):
`%APPDATA%\nvm` (no source found for any nvm-windows release defaulting there — the installer's
own script defaults the root under local application data); `%ProgramFiles%\Volta` (holds the
`volta.exe` binary, not a Node or provider CLI); asdf on native Windows (no native build exists;
the POSIX shims row is untouched); `%USERPROFILE%\.volta` on win32 (the POSIX analogy, unsourced
for Windows — Volta's Windows home is under local application data).
