## Planner decisions recorded for this plan

These close three of the five open questions 06-RESEARCH left to the planner. Each is a stated
rationale, not a deferral.

- **Q3 — version-walk depth: keep the walk, bound the win32 emission to the newest 3 version
  directories per root. POSIX stays unbounded and unchanged.**
  Reason: `stat` is slowest on Windows and D-09 already grows the location count, so an unbounded
  walk multiplies the cost on exactly the platform that can least afford it. The walk is kept
  rather than dropped because a broken `PATH` is the case it exists for — research row P-06 shows
  the nvm-windows symlink directory is added to `PATH` by the installer, so `where.exe` already
  finds an nvm-managed Node when `PATH` is intact, which makes the walk a fallback rather than the
  primary route. Bounding to 3 is a COST bound chosen by the planner, not a measurement, and the
  code comment must say so. The existing lexical reverse sort is NOT semver-correct (a v9 entry
  sorts after a v10 entry); that is pre-existing POSIX behaviour, CMP-01 says leave it alone there,
  and it is mirrored on win32 for symmetry rather than fixed — fixing it is not RES-01's job and
  would be a silent behaviour change on macOS/Linux.
- **Q4 — the provider-adjacent node sibling: keep `path.dirname` host-flavoured, move it into the
  thin impure caller, and pass the resulting DIRECTORY into the pure builder.**
  Reason: `command-resolution.test.ts:98-107` records that this derivation is host-flavoured BY
  DESIGN and cites the real `windows-latest` red that taught it — on a real Windows host the
  module is win32-flavoured and the derivation is correct. But leaving the derivation INSIDE the
  pure builder would make its win32 row unassertable on the Linux runner, which is the exact hazard
  D-05 exists to kill. Splitting it resolves both: the host-flavoured `dirname` stays where its
  recorded rationale applies, and the pure builder receives literal directories it can spell for
  the target platform. D-05's sweep names "every `path.join`" and does not name `dirname`; this
  records the exception in code so a later reader does not "finish the sweep".
  The sibling also gains the extension ladder on win32 — a bare `node` beside a `claude.cmd` is
  not a Windows executable name.
- **Q5 — `%ProgramFiles(x86)%\nodejs`: KEEP, tagged as an assumption in the code comment.**
  Reason: the variable is standard and the row costs one `stat` that PERF-03's cache absorbs, but
  no first-party statement ties a current Node MSI to it, so it cannot be tagged verified. The
  justification that keeps it alive is WOW64 bitness: on 64-bit Windows a 32-bit process sees
  `%ProgramFiles%` pointing at the x86 tree while a 64-bit process does not, so reading BOTH
  variables is the arm that survives whichever bitness Caido's backend host turns out to be. That
  reasoning goes in the comment beside the row.

**Rows DROPPED under D-12 and recorded as explicit non-claims in the code** (a later reader must
find the reason beside the table, not have to re-derive it):
`%APPDATA%\nvm` (no source found for any nvm-windows release defaulting there — the installer's
own script defaults the root under local application data); `%ProgramFiles%\Volta` (holds the
`volta.exe` binary, not a Node or provider CLI); asdf on native Windows (no native build exists;
the POSIX shims row is untouched); `%USERPROFILE%\.volta` on win32 (the POSIX analogy, unsourced
for Windows — Volta's Windows home is under local application data).
