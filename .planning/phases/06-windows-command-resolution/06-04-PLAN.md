## Planner decisions recorded for this plan

- **`extractHomeDir` stays platform-blind (D-06, locked).** One string in, no injected platform.
  It accepts both Windows spellings for the same reason `isAbsolutePath`'s `undefined` arm does:
  the function is reachable from a provider status check at plugin load, before the runtime probe
  sets the host facts, so every pre-probe call site would pass `undefined` anyway and the function
  would need a shape-sniffing arm regardless — with more ceremony around it.
- **A traversal segment yields `undefined` rather than a collapse.** The existing POSIX arm rejects
  a path containing a parent-directory traversal by normalising first and then failing the prefix
  test. The Windows arm reaches the same outcome by an explicit rejection rather than by adding a
  second, drive-aware normaliser: if any segment of the remainder is a single or double dot, return
  `undefined`. This matches the module's stated allow-list discipline — return `undefined` for
  anything unrecognised rather than guessing — and avoids shipping a path normaliser this phase has
  no other use for.
- **Only a profile directory literally named `Users` is recognised,** matched case-insensitively
  because Windows is. A redirected or non-default profile root is deliberately NOT recognised; that
  is a recorded non-claim, not a gap to fill by guessing.
- **The dedup fold applies on the literal win32 platform only — never on `undefined`.** D-07's own
  reasoning is that a missed dedup costs one extra existence check and never a wrong answer, while
  an over-eager fold could DROP a real candidate. macOS is case-insensitive by default and Linux is
  not, so folding on an unknown platform would risk collapsing two genuinely distinct POSIX paths.
  The asymmetry with D-08's union-when-unknown rule is deliberate and stated: there, the cheap
  failure was to emit an extra candidate; here, the cheap failure is to emit a duplicate.
