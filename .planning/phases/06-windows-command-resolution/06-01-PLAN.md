## Planner decisions recorded for this plan

- **Discretion — where `joinPath` lives: `platform.ts`.** Reason: `platform.ts`'s header states
  two mechanically-checkable properties (zero I/O, zero imports) that `joinPath` satisfies, and
  `getTempRoot` in the same file already strips separators by hand *for exactly this reason* —
  the Linux runner's `path` flavour would leave a Windows-shaped separator untouched, making the
  win32 case untestable where it matters. The CONTEXT's counter-argument ("it would then hold
  data-adjacent logic") is answered: `joinPath` knows only which character separates segments and
  carries no Windows install DATA. The catalogue stays in `command-resolution.ts`, which is where
  04-D-03's SHAPE-versus-DATA line puts it.
- **`getWindowsNamedRoots` also lives in `platform.ts`,** for the same reason
  `getHomeDirCandidates` already does: it ships variable NAMES only. The suffix lists built from
  those roots stay in `command-resolution.ts`.
- **Env-variable casing.** Windows spells three of these roots in mixed case (`ProgramFiles`,
  `ProgramFiles(x86)`, `ProgramData`) while libuv's back-fill list uses SCREAMING case. Windows'
  own `process.env` is case-insensitive, but the Linux unit test does a case-SENSITIVE object
  lookup. Both spellings are therefore read, native spelling first, first non-empty wins — so the
  test can assert the canonical spelling and the real platform works under either.
- **The tracer was split; the PLAN was not.** This plan is the heaviest slice in the phase and the
  one every other plan depends on, so the D-05 sweep of the impure version walk was lifted out of
  the tracer into its own task (T-06-01B). The seam is natural: the tracer proves the NEW
  end-to-end path, the sweep converts the LEGACY impure walk, and nothing in the tracer's own
  evidence depends on the sweep — the CMP-01 proofs pass literal `versionCandidatesByHomeDir`
  values, so they never touch the walk. Splitting the tracer keeps the tracer property intact:
  T-06-01 still leads and still runs one Windows resolution through every layer.
  Splitting the PLAN was considered and declined. It would move the wave graph — 06-02, 06-03 and
  06-04 all name `06-01` in `depends_on`, and a second wave-1 plan touching the same two files
  would violate the zero-`files_modified`-overlap rule for its own wave. That is a structural
  replan, not a targeted fix, and the cost lands on the part of the phase that is already correct.
  The estimate is unchanged at 95000: the work content is identical, only its partition into tasks
  moved, and sitting just under the budget is accepted knowingly — the mitigation is per-task
  tractability, which is what the split buys, not a smaller total.
  **Read that margin as uncalibrated, not as measured.** The arithmetic `95000/100000 = 0.95` is
  exact; its PREDICTIVE value is not, and it should not be cited downstream as though it were a
  measurement. Phase 05 is the only completed phase carrying an `actuals` block, and those six
  samples record `chars/4` over the files each plan changed — a proxy for OUTPUT SIZE, which
  `05-04` and `05-05` both caveat in their own summaries as measuring *"the FILES touched, not the
  work done"*. That is a different quantity from the agent-context consumption `estimate.tokens`
  projects, so it cannot calibrate this ratio in either direction. No project-local factor relating
  projection to actual context use exists yet; `confidence: low` in the frontmatter is the honest
  reading, and a 5% margin is inside the noise of an uncalibrated projection rather than headroom
  anyone has demonstrated. Phase 06's own actuals are the first samples that could begin to
  calibrate it — and only if they are recorded on a context basis rather than the output-size basis
  Phase 05 used.
- **`platform: undefined` (pre-probe) unions both arms,** POSIX rows first then win32 rows. This
  is the same union-when-unknown rule as `isAbsolutePath`, D-06, D-08 and D-13. It is
  CMP-01-safe on POSIX because `USERPROFILE`/`APPDATA`/`LOCALAPPDATA` are unset there, so every
  win32 row is skipped and the emitted list is byte-identical to today's.

    **1. `packages/backend/src/platform.ts` — add `joinPath` (D-05).**
    Signature: `export function joinPath(input: { platform: Platform | undefined; segments: string[] }): string`.
    The separator is derived ONLY from `input.platform`: a backslash when it is the literal
    `"win32"`, a forward slash otherwise (including `undefined`). Trim each segment; drop any
    segment that is empty after trimming. Join the survivors with the separator, and where a
    survivor already ends with either separator spelling or the next survivor already begins with
    one, emit exactly one separator at that seam rather than two. Preserve the first surviving
    segment's own leading separator verbatim. Do NOT normalize `.` or `..` — the POSIX suffix
    lists contain neither, and adding normalization would break the byte-identity proof in T-06-02.
    Do NOT read the separator from the `path` module's separator property — that reports the
    HOST's flavour and would make every win32 assertion a test of the Linux runner, which is the
    exact bug this function exists to eliminate.
    The header comment must carry the evidence, matching `getTempRoot`'s and `normalizePosixPath`'s
    house style: state that Caido's LLRT `path` declares no `posix` and no `win32` namespace at
    all (verified against `@caido/quickjs-types@0.25.4`, `src/llrt/path.d.ts`, whose
    `PlatformPath` interface returns zero matches for either name), so the one-line namespace fix
    does not exist on the shipping runtime; and state that the POSIX output is asserted
    byte-identical to the module-based join it replaces, per D-05 and 06-CONTEXT § Specific Ideas.

    **2. `packages/backend/src/platform.ts` — add `getWindowsNamedRoots` (D-09's input shape).**

    `localAppData`, `programFiles`, `programFilesX86`, `programData`. Export
    `getWindowsNamedRoots(input: { env: Record<string, string | undefined> }): WindowsNamedRoots`.
    Each field reads its env variable names in order and takes the first whose trimmed value is
    non-empty; a field with no non-empty value is left absent rather than set to an empty string.
    The name lists, exactly: `userProfile` from `USERPROFILE`; `appData` from `APPDATA`;
    `localAppData` from `LOCALAPPDATA`; `programFiles` from `ProgramFiles` then `PROGRAMFILES`;
    `programFilesX86` from `ProgramFiles(x86)` then `PROGRAMFILES(X86)`; `programData` from
    `ProgramData` then `PROGRAMDATA`. Do NOT add a `SystemRoot` field — D-02 gives that variable
    to `getWhichCommand`, and two readers of one variable is the duplication this file's
    "Don't Hand-Roll" discipline forbids.
    Comment it with three facts: (a) per 04-D-03 this ships variable NAMES only, the suffix lists
    built from them stay in `command-resolution.ts`; (b) Phase 3's P3-VARS measured `USERPROFILE`,
    `APPDATA` and `LOCALAPPDATA` all present and non-empty in the parent process on
    windows-latest, citing `.planning/phases/03-ci-spike-prove-llrt-basics-on-windows/03-FINDINGS.md`
