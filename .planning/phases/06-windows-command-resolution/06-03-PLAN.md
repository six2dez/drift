## Planner decisions recorded for this plan

- **Discretion — where the ranking helper lives: `platform.ts`, beside the extension constant it
  reads.** Putting it in `command-resolution.ts` would force that module to import the ordered
  extension list from here, splitting one ordering decision across two files — which is precisely
  the "second hardcoded order" hazard 06-CONTEXT names as a defect. The helper carries no Windows
  install DATA: it knows only a preference order it reads from an existing constant, so
  04-D-03's SHAPE-versus-DATA line is not crossed.
- **`platform: undefined` on `getWhichCommand` and `rankPathSearchHits` takes the POSIX arm — and
  this is NOT the POSIX default D-08 rejected.** Only one binary can actually be spawned, so there
  is no union answer available here. Choosing the POSIX arm pre-probe reproduces today's behaviour
  on every platform exactly, which is what CMP-01 requires; skipping the search entirely would be
  a real macOS/Linux regression, because a binary that lives only on `PATH` and in none of the
  known install locations would stop resolving during a pre-probe provider check. On Windows
  pre-probe the POSIX binary simply fails to spawn and resolution falls through to the candidate
  walk — which D-08's union roots have now made productive, so this arm costs Windows nothing it
  does not already lose today. The distinction from D-08 is that D-08's default DID have a union
  answer available and rejecting it was free; here it is not.
- **Q2 — the no-match informational line's stream is not answered, it is designed around.** Neither
  Microsoft's documentation nor the secondary reference states whether that sentence goes to
  standard output or standard error. Two independent guards make the code correct under either
  answer: the existing exit-code gate in `resolveCommand`, and this plan's extension-termination
  filter. The second guard is the one that survives a future loosening of the first, and it is the
  same mechanism that discards a partial final line above the output buffer cap. Both are asserted
  in tests. This is cheaper than the answer and does not decay.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| PATH-search tool standard output → path consumer | Untrusted text crosses here. Any line surviving the ranker is handed to a filesystem existence check and can become a spawn target. |
| parent process env → the search binary's own path | The system-root variable determines which binary is executed to perform the PATH search. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-T10 | Tampering | `rankPathSearchHits` input | high | mitigate | A non-path line reaching a path consumer is the concrete failure this helper exists to prevent: the tool's no-match informational sentence, and the partial final line the bounded output buffer leaves above its cap. Two independent guards — the exit-code gate at the call site and the extension-termination filter here. Gate: the literal informational-sentence test in T-06-07. |
| T-06-T11 | Spoofing | `getWhichCommand` win32 arm | medium | mitigate | Resolving the search binary through the bare name alone would let any directory earlier on `PATH` supply a substitute. Deriving the absolute path from the machine's own system-root variable removes that window for the normal case. The bare-name fallback remains as the arm that survives a runtime that does not populate the variable — a stated, tested trade-off rather than an oversight. |
| T-06-T12 | Tampering | system-root variable value | medium | accept | A hostile system-root value redirects the search binary.
