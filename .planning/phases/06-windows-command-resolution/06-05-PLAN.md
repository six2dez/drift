## Planner decisions recorded for this plan

- **Q1 — the win32 PATH-search timeout is 5000 milliseconds.**
  This is the phase's largest unsourced item and the decision is made on bounds, not on a guess.
  Two anchors already exist in this codebase: the POSIX value is 1000 milliseconds at the
  PATH-search site, and the module's general spawn helper caps at 10000 milliseconds, which is the
  highest timeout this codebase already sanctions. 5000 sits strictly between them, so the number
  is bounded by values the project already accepts rather than invented. A third bound confirms it
  is not too large: the resolution cache's negative entry lives 30 seconds, so a timeout longer
  than that would let a single cold miss cost more than its own cache lifetime — 5000 is well
  inside that.
  **The code comment must say plainly that this is headroom, not a measurement**, in the same voice
  Phase 3's findings use for their vehicle caveat. The research explicitly warns against upgrading
  the phrasing: describing the Windows search tool as "measurably slower" would be a claim this
  project cannot back, because no such measurement was found in this repository or in any
  first-party source. Say instead that no latency figure exists, name the two anchors, and say the
  number is revised on a real-machine report in Phase 9/10.
- **The POSIX timeout literal is extracted to a named constant with its value unchanged.** A
  platform ternary reading two named constants states the asymmetry; a ternary with one bare
  literal hides it. The extraction is a rename, not a behaviour change, and the value is asserted
  to still be 1000.
- **The console-window flash is marked, not fixed.** This plan ADDS a Windows spawn on a hot path,
  so it also adds a console-window flash that a later phase removes. 06-CONTEXT § Specific Ideas
  requires the site to be marked so that phase can find it by search rather than re-inventorying
  every spawn. The research confirms the suppression option is not present in the runtime's
  declared spawn options at all, so this is a real problem to solve later and not a one-line fix —
  say that at the marker.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| PATH-search subprocess stdout → path consumer | Untrusted text from a spawned process crosses into a value that is existence-checked and later spawned. |
| parent process env → the search binary's own path and the home-directory set | Environment values determine both which binary is executed and which directory tree is searched. |
| user-configured provider command → the search binary's argument list | A user-controlled string becomes an argument to a spawned process. |
