       The grep patterns must not match themselves, or the gate fails permanently on its own source: write them as the extended regexes `CAIDO_(TOKEN)` and `secret(s)\.` — as literal text neither contains the string it detects, while as regexes both match it exactly. Combine them into one `grep -nE` alternation over both files.

       **The gate must branch three ways, not two.** `grep` exits 0 on a match, 1 on no match, and **2 when a target file is missing or unreadable**. A two-branch gate ("if grep succeeds, fail; otherwise pass") routes that 2 into the pass branch and green-lights a renamed or deleted target. D-10 keeps this gate specifically so the property survives Phases 4-8 editing these files, and a rename is exactly the edit it must not sleep through; `01-06` recorded the general shape of this failure — a grep returning nothing looks identical to a proof that failed. So build it as:
         - First assert both targets exist, so a rename fails loudly rather than being inferred from an exit status: `for f in .github/workflows/windows-llrt-probe.yml scripts/windows-llrt-probe.mjs; do test -f "$f" || { echo "gate target missing: $f"; exit 1; }; done`.
         - Then capture grep's status explicitly rather than branching on its success. `shell: bash` resolves to `bash --noprofile --norc -eo pipefail {0}`, so `-e` is active and a bare non-zero grep would abort the step before any branch could run. The `|| status=$?` form is the `-e`-safe idiom because the left side of `||` is a condition context: `status=0` then `grep -nE '<alternation>' <file1> <file2> || status=$?`.
         - Branch on `status` with three arms: `0` → a match was found, echo an explanatory message and `exit 1`; `1` → clean, echo a confirmation naming both scanned files and fall through; anything else, including `2` → echo that the gate could not read its targets and `exit 1`. Do not collapse the third arm into the second.
       Add a comment above the branch stating why the third arm exists, since a future editor will otherwise "simplify" it back into an if/else.

       Word every echo so it does not itself contain either forbidden literal — say "a Caido token reference or a GitHub secrets expression". Place this step before the probe step so it fails fast and before anything could be printed. Comment why this gate outlives the spike: Phases 4-8 will edit these files, and the gate is what keeps the property true through those edits rather than being a one-time review. Plan 03-04 proves this gate actually bites by tripping it deliberately on a throwaway branch, so keep the step name stable — that plan reads the failing step by name from the API.

    4. `Run LLRT Windows primitive probe` — `shell: bash`, running the probe and teeing its merged output with `node scripts/windows-llrt-probe.mjs 2>&1 | tee probe-results.txt`. Comment three things. First, `shell: bash` is mandatory and not stylistic: GitHub Actions maps it to `bash --noprofile --norc -eo pipefail {0}` on every OS including Windows, and `pipefail` is what makes the pipeline return the probe's exit code instead of `tee`'s — under the default `pwsh` or `cmd` the probe could report FAIL and the step would still be green. Second, `2>&1` folds stderr into the artifact; the probe writes its counted status lines to stdout only, but an uncaught runtime error would surface on stderr and must not be lost. Third, the exit-code contract: 0 means both P0 assertions passed and P1-CMD was conclusive; 1 means P0-ENV failed, P0-TMP failed, or P1-CMD could not be classified. Note that a non-zero exit here is a legitimate recorded finding rather than a broken job — D-05 through D-07 define which outcomes gate.
