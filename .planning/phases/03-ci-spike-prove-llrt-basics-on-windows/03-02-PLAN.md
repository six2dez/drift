    1. `Checkout` — `actions/checkout@v5` (D-04; matches `ci.yml:30`).

    2. `Setup Node` — `actions/setup-node@v5` (D-04; matches `ci.yml:39`), `node-version: '24'`, quoted as `ci.yml` quotes its matrix values. No `cache:` input, no `pnpm/action-setup` step, and no install step. Comment the omission, because it is a deliberate divergence from `ci.yml`'s shape and a reader will otherwise assume it was forgotten: the probe imports Node built-ins only and has zero dependencies, so a `pnpm install --frozen-lockfile` here would add roughly a minute of Windows runner time plus a failure surface that could turn this job red for reasons that say nothing about the seven assertions — exactly the noise D-03 separates this workflow to avoid. Proving `pnpm install` on Windows is Phase 9's job (CI-01), whose purpose is build and vitest. Also note in the comment that D-04's fourth pin, `pnpm/action-setup@v6`, is not used here for that reason, and that any future edit adding pnpm to this workflow must use `@v6` to stay aligned with `ci.yml:36`.     3. `Assert no secret material is reachable (D-10)` — `shell: bash`, a `run: |` block in the `release.yml:15-20` shape. It scans both of this phase's files, `.github/workflows/windows-llrt-probe.yml` and `scripts/windows-llrt-probe.mjs`, and fails the job if either contains a Caido token reference or a GitHub secrets expression. The grep patterns must not match themselves, or the gate fails permanently on its own source: write them as the extended regexes `CAIDO_(TOKEN)` and `secret(s)\.` — as literal text neither contains the string it detects, while as regexes both match it exactly. Combine them into one `grep -nE` alternation over both files; if grep succeeds, meaning a match was found, echo an explanatory message and `exit 1`; otherwise echo a confirmation. Word the echo messages so they do not themselves contain either forbidden literal — say "a Caido token reference or a GitHub secrets expression". Place this step before the probe step so it fails fast and before anything could be printed. Comment why this gate outlives the spike: Phases 4-8 will edit these files, and the gate is what keeps the property true through those edits rather than being a one-time review.

    4. `Run LLRT Windows primitive probe` — `shell: bash`, running the probe and teeing its merged output with `node scripts/windows-llrt-probe.mjs 2>&1 | tee probe-results.txt`. Comment two things. First, `shell: bash` is mandatory and not stylistic: GitHub Actions maps it to `bash --noprofile --norc -eo pipefail {0}` on every OS including Windows, and `pipefail` is what makes the pipeline return the probe's exit code instead of `tee`'s — under the default `pwsh` or `cmd` the probe could report FAIL and the step would still be green. Second, the exit-code contract: 0 means both P0 assertions passed and P1-CMD was conclusive; 1 means P0-ENV failed, P0-TMP failed, or P1-CMD could not be classified. Note that a non-zero exit here is a legitimate recorded finding rather than a broken job — D-05 through D-07 define which outcomes gate.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repository content → GitHub Actions runner | The workflow and probe execute with runner privileges on every push to every branch |
| third-party action → runner | Each `uses:` pulls code the repository does not control |
| `GITHUB_TOKEN` → repository | The job's token can act on the repo within its granted permissions |
| probe stdout → public artifact | Artifact contents are world-readable on a public repository |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-03 | Tampering | third-party action supply chain | mitigate | The workflow uses only `actions/checkout@v5`, `actions/setup-node@v5` and `actions/upload-artifact@v5` — all GitHub-owned and all already trusted by `ci.yml` at the identical majors (`ci.yml:30`, `:39`, `:64`).
