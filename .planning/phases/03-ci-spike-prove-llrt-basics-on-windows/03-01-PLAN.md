<objective>
Create `scripts/windows-llrt-probe.mjs` — the zero-dependency Node ESM probe that answers all seven LLRT/Windows assertions (CI-02) — and add a targeted `.gitignore` entry for its local output file.

Purpose: This probe is the instrument the entire Windows port is calibrated against. Phases 4-8 pick their spawn and env-injection architecture from what it measures. Drift today never passes an `env` option to `spawn()` at all (both production call sites, `index.ts:1191` and `index.ts:2188`, pass only `stdio`; environment injection runs through a `#!/bin/bash` wrapper that `export`s variables and `exec`s). That wrapper cannot exist on Windows, so P0-ENV is not confirming an existing mechanism — it is proving the *replacement* mechanism works before code is written on top of it. That is why D-05 makes a P0-ENV failure a project-stopping blocker.

Output: `scripts/windows-llrt-probe.mjs` (new file in a new top-level directory — `scripts/` does not exist in this repo yet) and one line in `.gitignore`.
</objective>

    HEADER. Shebang `#!/usr/bin/env node` (inert on Windows, present for consistency with `mcp-server.mjs`), then a block docblock stating: what the file is, that it is invoked as `node scripts/windows-llrt-probe.mjs`, that the runtime vehicle is **Node.js, not LLRT** and why (no standalone LLRT Windows binary exists — upstream dropped it at v0.6.0-beta and `caido/dependency-llrt` has no published releases), and that the file is deleted in Phase 9 when CI-01 lands (D-02).

    IMPORTS — zero npm dependencies, Node built-ins only. One import must be **bare and stay bare**: `import { tmpdir, platform } from "os";`. Put a comment directly above it saying the un-prefixed specifier is deliberate because P2-OS's entire assertion is that the bare specifier resolves — prefixing it to `node:os` would make P2-OS assert nothing. All other imports use the `node:` prefix (`node:child_process` for `spawn`, `node:fs` for `existsSync`/`writeFileSync`/`unlinkSync`, `node:path` for `join`, `node:crypto` for a named `randomUUID` import). Use the named `randomUUID` import rather than a default `crypto` import so the readonly global `crypto` is not shadowed — P3-UUID must be able to test the `globalThis.crypto` surface and the `node:crypto` surface separately.

    OUTPUT GRAMMAR — SINGLE EMISSION, SUMMARY-ONLY. Three emitters:
      - `info(id, detail)` writes `INFO [<ID>]: <detail>` to stdout the moment it is called. Unlimited; `INFO` is the probe's progress and diagnostic channel, and it is what makes a hung Windows run diagnosable from a partial log.
      - `pass(id, detail)` and `fail(id, reason)` are **recorders, not printers**. Each pushes `{ id, status, detail }` onto a module-level `results` array and prints nothing at call time.
      - The `=== Summary ===` block at the end of `main` is the **only** place in the file that produces a line matching `^PASS [<ID>]: ` or `^FAIL [<ID>]: `.

    The single-emission rule is load-bearing and must be stated in a comment directly above the emitters, because a future reader will otherwise "helpfully" add an inline print. CI-side verification in plans 03-03 and 03-04 counts `grep -cE "^(PASS|FAIL) \[<ID>\]:" probe-results.txt` over the whole downloaded artifact and requires exactly 1 for each of the seven IDs. If `pass`/`fail` also printed at call time, every one of those counts would be 2 and the contract would be broken by construction. Do not add an inline status print "for visibility" — that is what `info` is for.

    Declare the seven IDs once as a module-level frozen array `ASSERTION_IDS` in the order `P0-ENV`, `P0-TMP`, `P1-CMD`, `P1-WHERE`, `P2-OS`, `P3-VARS`, `P3-UUID`. The summary block iterates that array rather than iterating `results`, so an assertion that never ran still produces a line.

    Every assertion must emit at least one `INFO [<ID>]:` line as it runs, and a failing assertion must emit its diagnostic detail as an `INFO [<ID>]:` line at the point of failure so the detail is in the artifact even if the process later dies. Write nothing to stderr deliberately — stderr stays reserved for uncaught runtime noise, which the workflow's `2>&1` still folds into the artifact.

    SPAWN HELPER — `spawnCapture(cmd, args, opts, timeoutMs)` returning a Promise that resolves (never rejects) to `{ surface, stdout, stderr, exitCode, error }` where `surface` is one of the four literals `"throw"`, `"error"`, `"close"`, `"timeout"`. Replicate `index.ts:852-875` exactly: a `settled` boolean guarding all paths, `clearTimeout(timeout)` on the `close` and `error` paths, and `try { child.kill("SIGKILL"); } catch { /* ignore */ }` on the timeout path. Wrap the `spawn()` call itself in `try`/`catch` and resolve with `surface: "throw"` — Node's CVE-2024-27980 guard throws **synchronously** out of `spawn()` for a `.cmd` target, so an async-only handler misses it entirely. Use `stdio: ["ignore", "pipe", "pipe"]`. Default timeout 5000 ms; P1-CMD passes 5000, P1-WHERE passes 5000. Never use a bare `catch (_) {}` — `no-empty` is configured `[2, { allowEmptyCatch: false }]` and an empty catch is a lint ERROR that would turn all four existing `ci.yml` legs red.

    P0-ENV (gates exit code — D-05). Build `sentinel` as the literal prefix `drift-probe-sentinel-` concatenated with `Date.now()`. Spawn `process.execPath` with `["-e", "process.stdout.write((process.env.SENTINEL || 'MISSING') + '|' + (process.env.PATH ? 'PATH-VISIBLE' : 'PATH-ABSENT'))"]` and `{ env: { SENTINEL: sentinel } }` — the `env` object carries that one key and nothing else. `process.execPath` is absolute so the child needs no `PATH` to start. Split the child's stdout on `|`: field 1 must equal `sentinel`; field 2 records whether the `env` option **replaced** the parent environment or merged into it. Emit that as an `INFO [P0-ENV]` line naming replace-vs-merge explicitly — Phases 4-8 need it to decide whether their spawn options must spread `...process.env`, and it is not recoverable from a bare PASS.
    On success: `pass("P0-ENV", ...)` naming the sentinel value and the replace/merge observation.
    On failure the result must be **conclusive about which mechanism broke**, because D-05 turns this into a blocker that halts Phase 4 and the blocker text has to name what is being decided. So on failure, retry once with `{ env: { ...process.env, SENTINEL: sentinel } }` and classify: if the merged retry succeeds, the `env` option is honoured but a fully-cleared environment block breaks the child on this host; if the merged retry also fails, the `env` option is not reaching the child at all. Emit an `INFO [P0-ENV]` line carrying the raw child stdout and any `error.code`/`error.message`, then `fail("P0-ENV", ...)` naming which of the two. Do not swallow the distinction into a generic message.

    P0-TMP (gates exit code — D-06). Call `tmpdir()` and `platform()` (the bare-imported `os` functions — deliberately not `process.platform`). Emit an `INFO [P0-TMP]` line carrying both raw values. FAIL if `platform()` is not the literal `"win32"`, or `tmpdir()` does not match `/^[A-Za-z]:[\\/]/`, or `existsSync(tmpdir())` is false; PASS only when all three hold. Keep the platform comparison against the single literal `"win32"` on one line — plan 03-04 mutates exactly that literal to prove the gate bites, so it must be a single unambiguous occurrence.

    P1-CMD (conclusive-or-fail — D-07). Write a real `.cmd` into `tmpdir()` at `probe-test-<Date.now()>.cmd` containing `@echo off` and `echo CMD_PROBE_RAN` with CRLF line endings, then `spawnCapture(cmdPath, [], {}, 5000)`. Emit an `INFO [P1-CMD]` line carrying the returned surface, exit code and raw stdout/stderr before classifying, so the raw observation is in the artifact independent of how it was classified. Then classify on the returned `surface`, and the classification — not the outcome — is what gates:
      - `"throw"` → conclusive. PASS, naming `spawn-threw-sync` and the raw `error.code` and `error.message` (EINVAL is expected on Node >= 18.20.2; EPERM/EBUSY from a Defender handle on a freshly written executable and ENOENT are equally conclusive).
      - `"error"` → conclusive. PASS, naming `spawn-error-event` and the raw code/message.
      - `"close"` with stdout containing `CMD_PROBE_RAN` → conclusive. PASS, naming `ran` and the exit code.
      - `"timeout"` → conclusive. PASS, naming `hung` and the timeout duration.
      - anything else — in particular a `"close"` whose stdout lacks the marker — is **not** one of D-07's three legitimate outcomes. `fail("P1-CMD", ...)` prefixed with the literal word `indeterminate`, carrying surface, exit code, and the raw stdout/stderr. This FAIL gates the exit code. Do not add a catch-all `pass()` — the superseded research skeleton calls `pass(...)` on every branch, which is precisely the defect D-07 exists to prevent.

    P1-WHERE (informational, no gate — D-09). Resolve the binary by absolute path, `join(process.env.SystemRoot ?? "C:\\Windows", "System32", "where.exe")`, because Git Bash's PATH on `windows-latest` may not include System32. Spawn it with `["node"]`. Split stdout on `/\r?\n/`, trim, drop empties. Emit an `INFO [P1-WHERE]` line with the line count and the JSON-stringified lines (the CRLF-parse evidence Phase 6 needs), then PASS naming the first line and whether it ends in `.exe`, or FAIL naming the surface and error when the spawn did not produce output. Either way this assertion must not influence the exit code.

    P2-OS (informational + mandatory vehicle label — D-08). The bare `os` import at the top of the file having succeeded is the assertion; reaching this function proves it. Emit an `INFO [P2-OS]` line naming the specifier that resolved. PASS with a detail that ends in the exact literal parenthetical `(node-vehicle; LLRT resolver verified by source analysis)` — LLRT's resolver calls `name.trim_start_matches("node:")`, so `"os"` and `"node:os"` are the same module there. The label is load-bearing, not decorative: without it a reader of the archived artifact will believe LLRT itself was exercised.

    P3-VARS (informational, no gate — D-09). Check `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`. Emit one `INFO [P3-VARS]` line per present variable carrying its value, then PASS if all three are non-empty or FAIL naming the missing ones. Print only these three variables by name — never iterate or dump `process.env`, whose contents on a hosted runner include tokens injected by the Actions runtime.

    P3-UUID (informational + mandatory vehicle label — D-08). Record `typeof globalThis.crypto?.randomUUID === "function"` and `typeof randomUUID === "function"` separately — LLRT and Node do not necessarily expose both surfaces, and Phase 4 needs to know which to target. Emit an `INFO [P3-UUID]` line carrying both booleans. PASS if either is true, FAIL if neither. The detail must end in the exact literal parenthetical `(node-vehicle; LLRT crypto surface unverified)` — unlike P2-OS there is no source-level LLRT confirmation for this one, and the label must not overstate.

    MAIN AND EXIT CONTRACT. Print a banner carrying `process.version`, `process.platform` and the vehicle caveat (pitfall 5: the `.cmd` EINVAL guard only exists on Node >= 18.20.2, so the version must be in the record). Run the assertions in `ASSERTION_IDS` order, awaiting the async ones, with the whole sequence wrapped in a `try`/`catch` so a thrown assertion cannot prevent the summary from being emitted.

    Then build the entire tail as ONE string and write it ONCE:
      - the literal line `=== Summary ===`;
      - one line per entry of `ASSERTION_IDS`, in that array's order, of the form `PASS [<ID>]: <detail>` or `FAIL [<ID>]: <reason>`, looked up from `results`. If an ID has no recorded result — because an earlier assertion threw, or because a code path forgot to record one — emit `FAIL [<ID>]: not reached — probe aborted before this assertion ran` and count it as a failure for exit-code purposes. This is what makes "exactly one line per ID" a structural guarantee rather than a hope, and it makes an aborted probe fail loudly instead of producing a short artifact that reads as a partial pass. If an ID has more than one recorded result that is a probe defect: emit a single `FAIL [<ID>]: duplicate result recorded` line for it and force a non-zero exit;
      - the final `PROBE PASSED:` or `PROBE FAILED:` verdict line, and on failure the documented fallback pointer (a minimal `.cmd` launcher that `set`s the variables, per the STATE.md blocker).

    Compute the exit code from the same resolved per-ID statuses the summary printed: 1 if `P0-ENV` is not PASS, or `P0-TMP` is not PASS, or `P1-CMD` is not PASS; 0 otherwise. Explicitly do not let P1-WHERE, P2-OS, P3-VARS or P3-UUID influence it.

    Emitting the whole tail as a single `process.stdout.write` is deliberate: under single emission this is the only region of output carrying the counted status lines, so its integrity is the artifact's integrity, and one write cannot be interleaved with anything else or partially ordered against stderr. Flush it before exiting — wrap that final `process.stdout.write` in a Promise and await its callback exactly as `mcp-server.mjs:699-706` does, and only then call `process.exit(code)`. A bare `process.exit()` truncates pending stdout writes, and under `2>&1 | tee probe-results.txt` on a Windows runner a truncated tail silently deletes every result line plus the verdict D-13 requires. There must be exactly one `process.exit(` call site in the file. Do not rely on setting `process.exitCode` and falling off the end — a stray un-cleared timer or a killed-but-not-reaped child would hang the job.
