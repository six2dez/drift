Create `packages/backend/src/fs-retry.ts` with a 4-6 line header comment stating that the *decision*
("is this retryable, how long do I wait") is pure and the *syscall* stays in `index.ts`, and that the
injected `sleep` is what makes the ladder assertable without a real filesystem lock. The module

Exports:

1. `export const FS_TRANSIENT_ERROR_CODES = ["EPERM", "EBUSY", "EACCES", "UNKNOWN"] as const;`
   Comment the provenance from libuv `src/win/error.c`: `ERROR_SHARING_VIOLATION` and
   `ERROR_LOCK_VIOLATION` → `EBUSY`, `ERROR_ACCESS_DENIED` → `EPERM`,
   `ERROR_ELEVATION_REQUIRED`/`ERROR_CANT_ACCESS_FILE` → `EACCES`, and **anything unmapped →
   `UNKNOWN`** — third-party AV filter drivers returning nonstandard NTSTATUS values land in
   `UNKNOWN`, which is why the roadmap names it. Also comment the deliberate **exclusions**:
   `ENOENT` (a missing parent is a real bug), `ENOSPC` and `EROFS` (retrying a read-only volume just
   delays the honest error by 1.5 s).

2. `export const FS_RETRY_DELAYS_MS = [50, 100, 200, 400, 750] as const;` — 5 retries, 1,500 ms
   total, 6 attempts including the first. Comment must record *why these numbers*, so a later phase
   can widen them on evidence rather than guess: graceful-fs budgets 60 s and npm/cli's arborist
   ~15.5 s, but both are batch tools where a long stall is invisible; this ladder wraps
   `startMcpServer`, which the user is watching, so a 15-second freeze on the "Start MCP" button is a
   worse outcome than an actionable error. Growth is geometric rather than graceful-fs's linear
   `+10 ms` because graceful-fs polls a `stat` between tries and this does not, so short delays would
   burn attempts inside one scan window. No jitter — Drift is a single writer to a private per-run
   directory, so there is no thundering herd and jitter would make the test non-deterministic.

3. `export function isTransientFsError(error: unknown): boolean` — reads
   `(error as { code?: unknown } | undefined)?.code`; returns `true` when it is a string in
   `FS_TRANSIENT_ERROR_CODES`. Then falls back to a substring check of the error message against the
   same four codes. Comment the justification for the substring fallback (this is the one place a
   message check is *not* laziness): Caido's LLRT does not use libuv — it uses `tokio::fs`/`std::fs`
   and throws through `or_throw_msg` with a human message rather than a structured `.code`, so the
   Win32 error is identical but the surfaced shape may not be. Mark it `[ASSUMED]` in the comment —
   inferred from `llrt_utils::result::ResultExt` usage in `caido/dependency-llrt`, not measured. Both
   forms are handled so either being wrong is harmless.

4. `export function getFsErrorCode(error: unknown): string` — returns the string `.code` when
   present, otherwise the first `FS_TRANSIENT_ERROR_CODES` entry found in the message, otherwise
   `"unknown"`. Used for retry logging and diagnostics.

5. `export type FsRetryOutcome<T> = { kind: "Ok"; value: T; attempts: number } | { kind: "Error"; error: string; attempts: number; lastCode: string };`
   Use the `kind` discriminated-union shape so `index.ts` can branch on it exactly as it branches on
   its inline `Result<T>` at `index.ts:1724-1728`. Do **not** import `Result<T>` — it is defined
   inline in `index.ts` (to avoid Zod, which crashes QuickJS) and is not exported.

6. `export async function withFsRetry<T>(operation: () => Promise<T>, deps?: { delays?: readonly number[]; sleep?: (ms: number) => Promise<void>; onRetry?: (info: { attempt: number; code: string; delayMs: number }) => void }): Promise<FsRetryOutcome<T>>`
   — defaults `delays` to `FS_RETRY_DELAYS_MS` and `sleep` to a `setTimeout`-backed promise. Loops
   `attempt` from `0` to `delays.length` inclusive; returns `{ kind: "Ok", value, attempts: attempt + 1 }`
   on success. On throw: records the error, breaks immediately when `!isTransientFsError(error)` or
   when `attempt === delays.length`, otherwise invokes `deps.onRetry` with the 1-based attempt index,
   the code from `getFsErrorCode`, and the delay about to be slept, then awaits `sleep(delays[attempt])`.
   Returns `{ kind: "Error", error: String(lastError), attempts, lastCode }` after the ladder is
   exhausted. It must **never** throw — same "always resolves" contract as `spawnAndWait`
   (`index.ts:1519-1529`).

The `onRetry` hook exists specifically so plan 04-08 can log every retry through `sdk.console` with
the code and attempt index, and so `attempts` reaches `getDiagnostics`. That logging is the agreed
mitigation for the one RUN-04 behaviour classified **N** (not provable in CI on any runner): a real
Defender lock. A future bug report then answers whether 1,500 ms was enough.

Pure modules never touch `sdk.console` — this module returns data and takes a callback; `index.ts`
does the logging.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Caido backend (LLRT) → local filesystem | The retried operation writes token-bearing runtime files; a retry loop that never terminates would stall the MCP-start path the user is watching |
| Third-party AV filter driver → Node/LLRT error surface | Nonstandard NTSTATUS values arrive here as `UNKNOWN`, an attacker-uncontrolled but unpredictable input |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-10 | Denial of Service | `withFsRetry` | mitigate | The ladder is a fixed, exported, finite array (`FS_RETRY_DELAYS_MS`, 5 entries, 1,500 ms total). There is no unbounded loop and no jitter. The `-t "gives up"` test asserts termination after exactly 6 attempts |
| T-04-11 | Denial of Service | `isTransientFsError` code set | mitigate | `ENOSPC` and `EROFS` are deliberately excluded so a full or read-only volume produces an honest error immediately instead of a 1.5 s stall on every MCP start |
| T-04-03 | Information Disclosure | retry logging via `onRetry` | mitigate | `onRetry` receives only an integer attempt index, an error **code** string, and a delay in ms — never the error message, never a path, never file contents. Plan 04-08 formats the log line from those three fields only |
| T-04-SC | Tampering | npm/pnpm installs | mitigate | `graceful-fs` and `write-file-atomic` are cited as **design references only** and must not be installed — both patch the global `fs`, which the Caido backend bundle cannot take. Phase 4 installs zero packages |
</threat_model>
