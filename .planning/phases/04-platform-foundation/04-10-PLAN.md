<objective>
Wire PERF-03's resolution cache into `packages/backend/src/index.ts`.

Purpose: today the two binary-resolution paths behave inconsistently. `lastNodeExecutable`
(`index.ts:119`, read at `:1559`) is an **infinite, never-invalidated** cache that survives settings
saves, MCP restarts and provider changes. `resolveCommand` (`index.ts:848`) has **no cache at all**
and re-runs `spawn("which")` plus the version-manager directory walk on every `checkProvider` call.
This plan puts both behind one bounded cache with a 5-minute positive TTL, a 30-second negative TTL,
total invalidation on any provider-command change, and a mandatory bypass on the user's manual
"Check" button.

Output: modified `packages/backend/src/index.ts`.

Validation rows owned (04-VALIDATION.md): the `index.ts` wiring behind PERF-03's five rows, all of
which are unit-proven in plan 04-07 — including `-t "bypass"`, which plan 04-07 made a testable
property of the module precisely because the `checkProviderAvailability` branch itself sits in the
untested `index.ts`.

Recorded so a later phase does not rediscover it the hard way: `process.execPath` is **absent** from
Caido's LLRT `process` object (source-verified). `getNodeExecutableCandidates`' `execPath` candidate
therefore contributes nothing in production. Nothing to fix here — the optional chaining already
handles it and `pushUniqueCandidate` drops `undefined` — but do **not** "restore" it as a Windows
candidate, and do not let Phase 6 assume it yields a free `node.exe`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User settings (`providers[*].command`) → binary resolution → `spawn` | A user-editable path decides which executable Drift launches; a cache outliving a command change would spawn a stale binary |
| Cached resolution results → `getDiagnostics` | Resolved binary paths cross into a surface a user may paste publicly |
| Filesystem (a newly installed CLI) → Drift's view of what is available | Negative caching can hide a real installation, an availability concern |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-20 | Tampering / Elevation | stale cached binary path after a command change | mitigate | `syncResolutionCacheSignature` clears the whole cache in `updateSettings` whenever any `providers[*].command` differs across the merge (ROADMAP SC-6). Seeded at init so the first save does not clear spuriously |
| T-04-21 | Denial of Service (self) | negative caching hiding a freshly installed CLI | mitigate | 30-second negative TTL plus a mandatory bypass on `checkProviderAvailability`, the user's manual Check button — pressed by exactly the person who just installed the CLI |
| T-04-25 | Tampering | absolute-path resolution being cached | mitigate | `resolveCommand`'s `path.isAbsolute` short-circuit stays **outside** the cache, so a deleted or replaced absolute path is re-checked on every call rather than lingering for 5 minutes |
| T-04-04 | Information Disclosure | `describeResolutionCache` in diagnostics | mitigate | Key names, ages in seconds, positive/negative markers and a clear count. The only path-shaped data is a binary path Drift itself resolved, already surfaced as `nodeExecutable`. No `process.env` enumeration |
| T-04-22 | Denial of Service | unbounded cache growth | accept | Keys are `node` plus one `cmd:<command>` per configured provider (at most five). Entries expire by TTL and the whole map is cleared on any command change |
| T-04-SC | Tampering | npm/pnpm installs | mitigate | Phase 4 installs zero packages; this plan adds only a local module import |
</threat_model>
