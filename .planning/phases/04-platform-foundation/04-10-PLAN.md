<objective>
Wire PERF-03's resolution cache into `packages/backend/src/index.ts`.

Purpose: today the two binary-resolution paths behave inconsistently. `lastNodeExecutable`
(`index.ts:119`, read at `:1559`) is an **infinite, never-invalidated** cache that survives settings
saves, MCP restarts and provider changes. `resolveCommand` (`index.ts:848`) has **no cache at all**
and re-runs `spawn("which")` plus the version-manager directory walk on every `checkProvider` call.
This plan puts both behind one bounded cache with a 5-minute positive TTL, a 30-second negative TTL,
total invalidation on any provider-command change, and a mandatory bypass on the user's manual
"Check" button.

Output: modified `packages/backend/src/index.ts`.

Validation rows owned (04-VALIDATION.md): the `index.ts` wiring behind PERF-03's five rows, all of
which are unit-proven in plan 04-07 — including `-t "bypass"`, which plan 04-07 made a testable
property of the module precisely because the `checkProviderAvailability` branch itself sits in the
untested `index.ts`.

Two facts verified against `index.ts` during planning, because getting either wrong makes the cache a
no-op in the place users look first:

1. `getDiagnostics` calls `await getNodeExecutable()` **directly** at `:2770`. It does not read
   `lastNodeExecutable`. So it is a full third consumer of node resolution and must be routed through
   the cache explicitly — there is no "if it also reads `lastNodeExecutable`" branch to take.
2. `getNodeExecutable` itself calls `resolveCommand("node")` at `:1537`, so once `resolveCommand` is
   cached under `cmd:<command>`, the node path is reachable under two keys. That is **not** double
   caching: `cmd:node` holds the unvalidated raw `which node` hit used as a candidate *input*, while
   `node` holds the executable that actually passed `--version` at `:1545-1552`. The `node` key is
   authoritative; task 1 records this in a comment and in a table.

**One extra change rides along, and it is not scope creep.** `resolveCommand`'s body is being moved
wholesale into the cache resolver callback, and that body contains PERF-04's **site 7**: an unbounded
total-volume accumulator at `index.ts:854`/`:862` (`let out = "";` … `out += d.toString();`). Every
earlier inventory in this phase missed it, because the natural query
`grep -n "stdout += \|stderr += "` is structurally blind to a variable named `out`. Plan 04-09 bounds
the six sites that query *can* see; this task bounds the seventh, under the same
`SPAWN_STDOUT_MAX_CHARS` cap with `head` retention. Doing it here rather than in 04-09 means the lines
are rewritten once, not twice.

Recorded so a later phase does not rediscover it the hard way: `process.execPath` is **absent** from
Caido's LLRT `process` object (source-verified). `getNodeExecutableCandidates`' `execPath` candidate
therefore contributes nothing in production. Nothing to fix here — the optional chaining already
handles it and `pushUniqueCandidate` drops `undefined` — but do **not** "restore" it as a Windows
candidate, and do not let Phase 6 assume it yields a free `node.exe`.
</objective>
