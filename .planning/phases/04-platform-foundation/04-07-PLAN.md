<objective>
Create `packages/backend/src/resolution-cache.ts` — PERF-03's bounded, invalidatable binary-resolution
cache with an injected clock — plus its sibling `resolution-cache.test.ts`.

Purpose and the asymmetry the executor must know first: **node resolution is already cached — but
infinitely, and with no invalidation at all.** `lastNodeExecutable` (`index.ts:119`) is set on
success and never cleared except inside `getNodeExecutable()` on total failure; it survives settings
saves, MCP restarts and provider changes. So for `node`, PERF-03 is *replacing an unbounded cache
with a bounded one* — a tightening. For providers, `resolveCommand` (`index.ts:848`) has **no cache
at all** and re-runs `spawn("which")` plus a version-manager directory walk on every `checkProvider`
call. Both must go through this one cache, or the phase ships two inconsistent behaviours.

**Deliberate shape choice recorded.** 04-RESEARCH proposes `createResolutionCache({ now, ttlMs })`
returning closures. `04-PATTERNS.md` § *No Analog Found* flags that **the backend has no
closure-factory precedent** — closure factories exist only in the frontend's Pinia stores, and the
backend's proven shape is `createXState(): PlainObject` + free functions taking that object
(`claude-print.ts:103-117`, `:140`). This plan takes the **state-object** shape. Rationale: it matches
the five existing pure modules, it keeps `now` an explicit per-call parameter (so a test never has to
reason about a captured clock), and it makes cache contents directly inspectable in assertions and in
`getDiagnostics`.

Output: `packages/backend/src/resolution-cache.ts`, `packages/backend/src/resolution-cache.test.ts`.

Validation rows owned (04-VALIDATION.md): PERF-03 `-t "within TTL"`, `-t "expires"`, `-t "negative"`,
`-t "invalidates on command change"`, `-t "bypass"`.
</objective>

Exports:

1. `export const RESOLUTION_POSITIVE_TTL_MS = 5 * 60 * 1000;` — 5 minutes. Comment: a resolved binary
   path is stable across a work session, and a stale hit costs at most one failed spawn because
   `getNodeExecutable` already re-walks when the cached path fails.
2. `export const RESOLUTION_NEGATIVE_TTL_MS = 30 * 1000;` — 30 seconds. Comment the trade-off
   CONTEXT.md names explicitly: **not** caching misses repeats the expensive walk (`readdir` + `stat`
   per version dir per home dir) precisely in the slow case; caching them means a freshly installed
   binary stays invisible for the TTL. 30 s bounds that window to something a user will not notice
   while collapsing the repeated walk during a burst of turns — and the mandatory bypass on the
   manual "Check" button is what makes any TTL choice safe.
3. `export type ResolutionCacheEntry = { value: string | undefined; storedAt: number };`
4. `export type ResolutionCacheState = { entries: Map<string, ResolutionCacheEntry>; signature: string; positiveTtlMs: number; negativeTtlMs: number; clears: number };`
   `clears` is a counter for diagnostics.
5. `export function createResolutionCacheState(options?: { positiveTtlMs?: number; negativeTtlMs?: number }): ResolutionCacheState`
   — TTLs default to the two constants; `signature` starts `""`; `clears` starts `0`.
6. `export function readResolutionCache(state: ResolutionCacheState, input: { key: string; now: number }): { hit: boolean; value: string | undefined }`
   — a miss returns `{ hit: false, value: undefined }`. An entry is live when
   `input.now - entry.storedAt < (entry.value === undefined ? state.negativeTtlMs : state.positiveTtlMs)`.
   An expired entry is deleted from the Map and reported as a miss.
7. `export function writeResolutionCache(state: ResolutionCacheState, input: { key: string; value: string | undefined; now: number }): void`
   — stores in place (mutating the Map is consistent with the backend's module-level-singleton norm
   and keeps `index.ts`'s call sites trivial).
8. `export async function resolveWithCache(state: ResolutionCacheState, input: { key: string; now: number; bypass?: boolean; resolve: () => Promise<string | undefined> }): Promise<string | undefined>`
   — when `bypass` is not true, returns the cached value on a live hit **without calling
   `input.resolve`**. Otherwise awaits `input.resolve()`, writes the result (including `undefined`,
   which is the negative cache), and returns it. With `bypass: true` it always calls `resolve` and
   always refreshes the entry. This is the single entry point `index.ts` uses from both
   `resolveCommand` and the node-resolution path.
9. `export function clearResolutionCache(state: ResolutionCacheState): void` — empties the Map and
   increments `clears`.
10. `export function buildProviderCommandSignature(providers: Record<string, { command?: string } | undefined> | undefined): string`
    — a deterministic string over the provider ids **sorted** and their `command` values, e.g.
    `id=command` joined by `\n`, with a stable placeholder for a missing command. Sorting matters:
    object key order must not produce a spurious signature change.
11. `export function syncResolutionCacheSignature(state: ResolutionCacheState, signature: string): boolean`
    — when `signature !== state.signature`, sets it, calls `clearResolutionCache`, and returns `true`;
    otherwise returns `false`. Comment that ROADMAP SC-6 requires invalidation on command change and
    that clearing the **whole** cache is deliberate — per-key invalidation invites a missed key, and
    the cache is at most a handful of entries.
12. `export function describeResolutionCache(state: ResolutionCacheState, now: number): string` —
    a one-line human-readable summary for `getDiagnostics`: entry count, each key with its age in
    seconds and whether the entry is positive or negative, and the `clears` count. **Names and ages
    only; never emit anything that is not already a binary path Drift resolved.**

Do not add `vi`-specific or test-only exports. Pure modules never touch `sdk.console`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User settings (`providers[*].command`) → binary resolution | A user-editable path decides which executable Drift spawns; a cache that outlives a command change would spawn a stale binary |
| Cache contents → `getDiagnostics` output | Resolved binary paths cross into a surface a user may paste publicly |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-20 | Tampering / Elevation | stale cached binary path after a command change | mitigate | `syncResolutionCacheSignature` clears the **whole** cache whenever any `providers[*].command` differs (ROADMAP SC-6). Whole-cache clearing is deliberate: per-key invalidation invites a missed key. Proven by `-t "invalidates on command change"` plus its unchanged-signature negative partner |
| T-04-21 | Denial of Service (self) | negative caching hiding a freshly installed binary | mitigate | Negative TTL is 30 s, and `resolveWithCache`'s `bypass` flag — wired to the user's manual "Check" button in plan 04-10 — always re-resolves. That escape hatch is what makes any TTL choice safe |
| T-04-22 | Denial of Service | unbounded cache growth | accept | Keys are `node` plus one per configured provider (at most five). No eviction policy needed; entries expire by TTL and the whole map is cleared on any command change |
| T-04-04 | Information Disclosure | `describeResolutionCache` in diagnostics | mitigate | Emits key names, ages in seconds, positive/negative markers and a clear count. The only path-shaped data is a binary path Drift itself resolved, which `getDiagnostics` already surfaces as `nodeExecutable` (`index.ts:2796`) |
| T-04-SC | Tampering | npm/pnpm installs | mitigate | Phase 4 installs zero packages; this module has no imports at all |
</threat_model>
