Create `packages/backend/src/activity-tail.ts` — PERF-02's incremental read of the MCP activity JSONL
file — plus its sibling `activity-tail.test.ts`.

Purpose: today `flushActivities` (`index.ts:2154-2185`) does `readFile(activityFilePath, "utf-8")`
and re-parses the **entire growing file** every 250 ms tick, on Caido's single-threaded event loop.
This module replaces the *input* to that loop, not its semantics: a byte cursor, a positional read,
and a byte-safe partial-line carry.

**Deliberate choice recorded:** this module owns the `open`/`stat`/`read`/`close` sequence rather than
leaving it in `index.ts`, with `open` injectable. That is a departure from "all I/O stays in
index.ts", and it is the right one here: `index.ts` has zero direct test coverage, and
`04-VALIDATION.md` grades the truncation-reset and no-new-bytes behaviours as **integration** tests
against a real `mkdtemp` file. Owning the I/O in a testable module is what moves those two rows from
bucket **N** to bucket **L**. The pure decisions (`planActivityRead`, `consumeActivityChunk`) are
still separately exported and separately tested.

Exports:

1. `export type ActivityCursor = { offset: number; partial: Buffer };`
2. `export function createActivityCursor(): ActivityCursor` → `{ offset: 0, partial: Buffer.alloc(0) }`.
3. `export const ACTIVITY_MAX_TICK_BYTES = 1024 * 1024;` — bounds the per-tick allocation. Comment
   that 1 MiB is generous: the writer emits one `JSON.stringify(event)` line per tool call
   (`mcp-server.mjs:82`, a single `appendFileSync`).
4. `export function planActivityRead(input: { cursor: ActivityCursor; size: number; maxBytes?: number }): { action: "reset" | "idle" | "read"; position: number; length: number }`
   — pure. When `input.size < input.cursor.offset` → `{ action: "reset", position: 0, length: min(size, maxBytes) }`
   (truncation or rotation: start over from byte 0). When `input.size === input.cursor.offset` →
   `{ action: "idle", position: cursor.offset, length: 0 }`. Otherwise
   `{ action: "read", position: cursor.offset, length: Math.min(size - cursor.offset, maxBytes ?? ACTIVITY_MAX_TICK_BYTES) }`.
5. `export function consumeActivityChunk(cursor: ActivityCursor, bytes: Buffer): { cursor: ActivityCursor; lines: string[] }`
   — pure, and the byte-safety core. `Buffer.concat([cursor.partial, bytes])`; find the **last**
   `0x0A` with `lastIndexOf`. When there is none, return the merged buffer as the new `partial` and
   an empty `lines` array. Otherwise decode only `merged.subarray(0, lastNewline).toString("utf-8")`,
   carry `merged.subarray(lastNewline + 1)` forward **as a Buffer**, and produce `lines` by
   `split("\n")` → `trim()` → drop empty — identical to `parseRuntimeActivityEvents`'s semantics,
   minus the JSON parse, which stays in `index.ts`. `offset` is passed through unchanged (the caller
   advances it by `bytesRead`). Comment Pitfall 4 explicitly: `JSON.stringify` does not escape
   non-ASCII, so carrying the remainder as a *string* would bake a permanent U+FFFD into any tool
   result containing an em-dash, an IDN hostname, or a non-ASCII response snippet.
6. `export type ActivityFileHandle = { stat(): Promise<{ size: number }>; read(buffer: Buffer, offset: number, length: number, position: number): Promise<{ bytesRead: number }>; close(): Promise<void> };`
7. `export async function readActivityTick(input: { filePath: string; cursor: ActivityCursor; maxBytes?: number; open?: (filePath: string, flags: string) => Promise<ActivityFileHandle> }): Promise<{ cursor: ActivityCursor; lines: string[] }>`
   — defaults `open` to `openFile`. Sequence: open with flag `"r"`; inside `try`, `stat()` for `size`;
   call `planActivityRead`; on `"idle"` return the cursor unchanged with no lines; on `"reset"`
   replace the cursor with a fresh one before planning the read position; allocate
   `Buffer.alloc(plan.length)` and call `read(buffer, 0, plan.length, plan.position)`; advance
   `offset` by `bytesRead`; feed `buffer.subarray(0, bytesRead)` to `consumeActivityChunk`. Close the
   handle in a `finally` with its own `catch` so a close failure cannot mask a successful read.
   Wrap the whole body so the function **never throws** — on any error return the *incoming* cursor
   and an empty `lines` array, preserving today's best-effort contract.

   Directly above the `Buffer.alloc(plan.length)` line, add an anchored comment stating: the buffer is
   sized **exactly** to the read length and `offset` is `0`, because LLRT's `FileHandle.read` ends in
   `dst_buf[offset..].copy_from_slice(&buf)`, and `copy_from_slice` panics in Rust unless the source
   and destination slice lengths match exactly — `validate_length_offset` only checks
   `length <= buffer_length - offset`, so a *smaller* explicit length passes validation and then
   panics. Never reuse one large buffer with a smaller per-read length. Also note the LLRT source
   comment `position: Opt<Option<u64>>, // -1 is not supported` — always pass a non-negative
   position. This comment is unobservable on Node and `04-VALIDATION.md` grades it as a
   static/code-review deliverable, so **the comment is the artifact**.

   Add a second comment on the `finally` close: a held handle blocks `rm(activityFilePath)` at
   `finalize()` on Windows with `EBUSY`, and 4 opens/second is negligible.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MCP server process → activity JSONL file → Caido backend parser | Tool results derived from the **target application's responses** cross here; content is attacker-influenced |
| Activity file size → Caido backend heap | An unbounded per-tick allocation would be a backend DoS on a single-threaded event loop |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-09 | Denial of Service | `readActivityTick` / `ACTIVITY_MAX_TICK_BYTES` | mitigate | Every read is clamped to `ACTIVITY_MAX_TICK_BYTES` (1 MiB) by `planActivityRead`, and the buffer is allocated to exactly that clamped length. A runaway writer cannot force an arbitrarily large single allocation |
| T-04-14 | Denial of Service | `consumeActivityChunk` partial buffer | accept | A single never-terminated line grows `cursor.partial` without bound. Accepted: the writer is Drift's own `mcp-server.mjs` doing one `appendFileSync(JSON.stringify(event) + "\n")` per tool call, the cursor dies with the turn, and the file is deleted at `finalize()`. Recorded rather than mitigated so a later phase can add a cap if the writer ever changes |
| T-04-15 | Tampering | JSON line parsing | mitigate | Line semantics are preserved exactly from `parseRuntimeActivityEvents`: bad JSON is skipped silently, never thrown. `index.ts` retains `seenActivityIds` as the correctness backstop — a truncation reset re-reads from byte 0, so re-delivery is unlikely but not impossible and the dedupe Set must **not** be removed as "now redundant" |
| T-04-16 | Denial of Service | held file handle | mitigate | Open and close per tick. A handle held across ticks blocks `rm(activityFilePath)` at `finalize()` on Windows with `EBUSY`, leaving a token-adjacent runtime file on disk |
| T-04-SC | Tampering | npm/pnpm installs | mitigate | Phase 4 installs zero packages; this module imports only `buffer` and `fs/promises`, both already imported by `index.ts` |
</threat_model>
