<objective>
Wire PERF-02's offset read and PERF-04's bounded accumulators into
`packages/backend/src/index.ts`.

Purpose: these two changes share a file and a code region (`sendCliMessage`'s
`new Promise` body and `spawnAndWait`), so they ship together rather than fighting over the same
lines in two waves. Both are pure replacements of an *input* or an *accumulation*, not semantic
changes — the activity dedupe, the tolerant JSON parse, the event emission, and every stdout/stderr
consumer stay exactly as they are.

PERF-02's motivation: `flushActivities` (`index.ts:2154-2185`) currently does
`readFile(activityFilePath, "utf-8")` and re-parses the **entire growing file** on every 250 ms
`setInterval` tick, on Caido's single-threaded event loop — the loop that also runs the RPC keep-alive
the watchdog depends on.

PERF-04's motivation: **seven** unbounded accumulator sites in a long-lived backend process — not
the four an early draft of this plan claimed, and not the six the draft after that claimed. This plan
owns six of them; plan **04-10** owns the seventh:

| # | Site | Declared | Appended | Mechanism | Owner |
|---|------|----------|----------|-----------|-------|
| 1 | `spawnAndWait` stdout | `:1522` | `:1524` | `appendBounded`, `head` | this plan, task 2 |
| 2 | `spawnAndWait` stderr | `:1523` | `:1525` | `appendBounded`, `tail` | this plan, task 2 |
| 3 | `sendCliMessage` stdout | `:2205` | `:2484` | `appendBounded`, `both` | this plan, task 2 |
| 4 | `sendCliMessage` stderr | `:2206` | `:2573` | `appendBounded`, `tail` | this plan, task 2 |
| 5 | `callMcpMethod` stderr | `:1201` | `:1295` | `appendBounded`, `tail` | this plan, task 3 |
| 6 | `callMcpMethod` `stdoutBuffer` | `:1200` | `:1268` | `drainCompleteLines` | this plan, task 3 |
| 7 | `resolveCommand`'s `out` | `:854` | `:862` | `appendBounded`, `head` | **plan 04-10, task 1** |

`grep -n "stdout += \|stderr += " packages/backend/src/index.ts` returns **five** matches today
(`:1295`, `:1524`, `:1525`, `:2484`, `:2573`). Two sites are invisible to that pattern: site 6
appends as `stdoutBuffer +=`, and **site 7 appends as `out +=`** — the variable inside
`resolveCommand`'s `which`/`where.exe` promise is named `out`, not `stdout`, so the inventory grep
never saw it. Task 2 converts sites 1-4 and task 3 converts sites 5-6, which is what makes the
`grep -c "stdout += \|stderr += " … returns 0` gate satisfiable at the same time as the
`appendBounded(` and `createBoundedBuffer(` count gates. An earlier draft asserted `0` for the first
and `4` for the other two, which cannot both hold.

**Read the scope of that zero literally.** `grep -c "stdout += \|stderr += "` returning `0` at the
end of this plan means *the five sites that pattern can see* are converted. It says nothing about
site 7, which plan 04-10 converts one wave later. Plan **04-11's Gate 7** is where the phase-wide
claim is graded, and it deliberately uses the broader `out += \|stderr += ` pattern (`stdout += `
contains `out += `, so the broader form is a strict superset) precisely so site 7 cannot hide behind
a variable name. Nothing in this plan may claim "no unbounded accumulator remains".

`callMcpMethod` is deliberately **not** scope-fenced. Its
`Math.min(currentSettings.processTimeoutSeconds * 1000, 10000)` timeout and `proc.kill("SIGKILL")`
bound the exposure **window** to ten seconds; they do not bound the **volume**, and a child writing
at pipe speed for ten seconds is a multi-hundred-megabyte allocation on a single-threaded runtime.
PERF-04's wording — "`stdout`/`stderr` accumulation … use bounded buffers with marked truncation" —
covers `:1201`/`:1295` without qualification.
