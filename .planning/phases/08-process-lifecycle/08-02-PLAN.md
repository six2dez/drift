## Recorded decisions

These are **decisions**, not observations. Each is written down so a later reader does not "improve" it
back into the shape it was deliberately moved away from.

**D-01 — the mechanism is a spawn, not a signal, and SC-2 is amended in place.**
`08-RESEARCH.md` § *Q2* source-verified that Caido's LLRT types the kill primitive's `pid` parameter as a
Rust `u32` and that rquickjs range-checks it through `f64`, so the canonical group-signalling spelling
raises an `Underflow` conversion error there — while working perfectly under Node, which is the only
vehicle any CI leg in this repository runs. That is Phase 5 finding L-4 recurring: green on every runner
the project has, broken in production. Phase 8 therefore builds the **spawn** form (`kill` with
`["-TERM", "--", "-<pid>"]`) and plan 08-05 amends ROADMAP SC-2 in place to name the mechanism and the
LLRT reason, per the Phase 5 SC-1 / Phase 7 SC-2 precedent (`05-CONTEXT.md` D-02). The static gate added
in T-08-06 is the vehicle-independent control that keeps the broken spelling out.
*Reversibility: reversible — the argv lives in one pure function with one consumer.*

**OQ-2 — the POSIX arm keeps BOTH signals, as defence against assumption A1.**
`killTree` issues the single-pid signal on the `ChildProcess` handle **first**, then spawns the group
kill. This is not belt-and-braces: it is specifically insurance against A1 (that the shipped Caido LLRT
might not honour `detached`). If `detached` silently failed, the group form signals a group that does not
exist and *nothing* dies; the single-pid rung converts that total regression into the partial one we
have today. Plan 08-01's spike closes A1, and this rung stays regardless — it costs one syscall.
*Reversibility: reversible.*

**OQ-4 — `cancelCliMessage` stays synchronous.**
It is declared `function cancelCliMessage(sdk, sessionId): Result<void>` and it returns to the frontend
immediately today. `killTree` is therefore **fire-and-forget**: it returns `void`, awaits nothing, and no
caller's signature changes. Awaiting a kill spawn inside a cancel would open a window in which an RPC is
pending while Caido's single-threaded runtime is not delivering `child_process` callbacks — the exact
starvation class the whole watchdog/keep-alive apparatus exists to work around (CLAUDE.md § *Anti-Patterns*),
introduced at the worst possible moment. SC-5's "cancellation semantics visible to the user are unchanged"
then holds **by construction** rather than by test.
*Reversibility: reversible.*

**D-P3 — the fire-and-forget spawn shape (no precedent in this repo; specified here).**
`08-PATTERNS.md` § *No Analog Found* records that every existing `index.ts` spawn is either awaited
(`spawnAndWait`) or long-lived and tracked (`activeProcesses`); a spawn that is deliberately neither is
new. The shape is fixed as: capture `proc.pid` once into a `const` at plan-build time; call the
single-pid rung; build the plan; on `{ kind: "none" }` log the reason and return; on `{ kind: "spawn" }`
call the **bare** `spawn` (not `spawnWithEnv` — the killer inherits the parent block correctly and has no
reason to carry a DRIFT env) inside a `try`/`catch` around the call itself; attach discarding `data`
handlers to both pipes so they cannot fill; attach `close` and `error` handlers that log value-free
lines; store the child in no map; return `void`.
*Reversibility: reversible.*

**D-P4 — `buildKillTreePlan` takes an `env` record, not a `systemRoot` scalar.**
This **overrules** `08-RESEARCH.md` § *Code Examples*, which drafts a `systemRoot?: string` scalar. The
scalar moves the `SystemRoot` / `SYSTEMROOT` dual-casing fallback out to `index.ts`, where no test this
project can run is able to reach it — reintroducing, for a Windows-only behaviour, exactly the
"unverifiable by construction" problem the pure-helper split exists to eliminate. `getWhichCommand`
(`platform.ts:255-294`) already solved the identical problem by taking an `env` record, and this phase
copies that precedent rather than inventing a weaker one. The call site becomes `env: readParentEnv()`,
which mirrors the shipped `selectComspec({ env: readParentEnv(), platform: host?.platform })` shape and
is assertable from `index.source.test.ts` in the same form.
*Reversibility: reversible.*

**`detached: true` on the provider spawn — rated `costly`.**
It is a one-line revert, but it is a real POSIX behaviour change reaching the entire shipping user base:
the provider child moves into its own process group and stops receiving signals delivered to Caido's
group (`08-RESEARCH.md` Pitfall 6). It is not rated `one-way`, and no `checkpoint:decision` is inserted
here, because plan 08-01's blocking `checkpoint:human-verify` already gated exactly this decision on a
measurement from real hardware. The counterweight is decisive and measured: without it, the
token-bearing MCP grandchild survives **every** cancel.

**1. Create `packages/backend/src/kill-plan.ts`.**

This task implements maintainer decision **D-01** (the mechanism is a spawn, not a signal) and
**OQ-2** (the POSIX arm keeps both signals); its `cancelCliMessage` shape implements **OQ-4** (the RPC
stays synchronous); and its builder signature implements **D-P4** (an `env` record, not a `systemRoot`
scalar). All four are recorded in full in this plan's § *Recorded decisions*.

Module header, following the four-paragraph `spawn-plan.ts` convention exactly: the purity claim stated
mechanically (zero I/O, no module state, exactly one import statement so `grep -cE '^import'` over the
file returns 1); the single import named as `./platform` and justified; the deliberately-NOT-imported
list — `os` and `process` (Phase 4 D-02 gives `index.ts` the one guarded runtime read), `path` (it resolves to
its POSIX flavour on the Linux CI runner and would corrupt a Windows path, the same reason
`platform.ts` spells the backslash join by hand), and `child_process` (a module that cannot spawn has no
hidden effect a test cannot see); and the why-this-lives-outside-`index.ts` paragraph, using the current
measured figure of **5,240 lines** rather than `spawn-plan.ts`'s stale "~4,900".

Add a fifth paragraph in the `spawn-plan.ts:40-80` measurement-recording style, quoting the A1 and A6
verdict lines from `08-SPIKE.md` verbatim with the Caido version and date that produced them. Do not
paraphrase a measurement.

Exports:

- `export type KillRung = "term" | "kill";`
- `export type KillTreePlan` — the discriminated union CLAUDE.md names as the house convention, keyed on
  `kind`, with arms `{ kind: "none"; reason: "no-pid" }` and
  `{ kind: "spawn"; file: string; args: string[]; windowsVerbatimArguments: boolean }`. The `spawn` arm
  mirrors `SpawnPlan`'s three projections so `index.ts` consumes both identically.
- `export const DEFAULT_TASKKILL = "taskkill.exe";` — the fallback bare name, spelled once, with the
  `DEFAULT_COMSPEC` note that reading the environment is the caller's job.
- `export function buildKillTreePlan(input: { pid: number | undefined; platform: Platform | undefined; env: Record<string, string | undefined>; rung: KillRung }): KillTreePlan`
- `export function shouldDetachProviderSpawn(platform: Platform | undefined): boolean`

Branch order is part of the contract and must carry a comment saying so:

- **Refusal first.** Return `{ kind: "none", reason: "no-pid" }` when `pid` is `undefined`, is not an
  integer (`Number.isInteger`), or is `<= 0`. This is SC-1's guard and it lives here and nowhere else —
  that is what makes it testable. A negative pid would be a group reference nobody asked for; `0` means
  "my own group" on POSIX, i.e. Drift signalling itself.
- **Then `win32`.** Read the system root from `input.env` under both `SystemRoot` and `SYSTEMROOT`,
  trimming each and taking the first non-empty (per D-P4 and the `getWhichCommand` precedent). Strip
  every trailing `\` or `/` by hand in a loop, so a root that already carries one does not produce a
  doubled separator and a bare `D:\` reduces to `D:` and yields the correct `D:\System32\...`. Emit
  `file` as `<root>\System32\taskkill.exe` when a root was found and `DEFAULT_TASKKILL` when none was,
  `args` as `["/pid", String(input.pid), "/t", "/f"]`, and `windowsVerbatimArguments: false`. Quote the
  Microsoft Learn definitions of `/t` and `/f` in the comment. State that there is no graceful rung on
  Windows — LLRT maps every signal name to one `TerminateProcess`, so a two-rung ladder there would be
  theatre — and that `true` for `windowsVerbatimArguments` would be a defect, because nothing in these
  args was escaped by this module.
- **Then POSIX, with `undefined` INCLUDED** as the fall-through. Emit `file: "kill"`, `args` as
  `["-KILL" | "-TERM", "--", "-" + String(input.pid)]` chosen by `input.rung`, and
  `windowsVerbatimArguments: false`. The comment must state three things: the negative argument is a
  **process group** reference and depends on the provider having been spawned detached (LLRT's
  `process_group(0)` makes pgid equal pid); `--` terminates option parsing so the negative operand is
  not read as a flag; and this is a spawn rather than the runtime's own negative-pid signalling form
  **deliberately**, naming `08-RESEARCH.md` § *Q2* and instructing the reader not to simplify it back.
  Note that `undefined` takes the POSIX arm because the POSIX arm is the one that must not regress
  (CMP-01), the same rule as `buildSpawnPlan`'s non-win32-first branch.

`shouldDetachProviderSpawn` returns `platform !== "win32"`, with the comment explaining that win32 does
not need it — `taskkill /t` walks `ParentProcessId` and is indifferent to process groups, while LLRT's
win32 arm sets `DETACHED_PROCESS` rather than `CREATE_NEW_PROCESS_GROUP` and would perturb the
console-attachment contract Phase 7 measured — and that `undefined` takes the POSIX arm for CMP-01.

**2. Create `packages/backend/src/kill-tree.posix.test.ts`.**

Gate with `describe.skipIf(process.platform === "win32")`. Preamble, in the
`mcp-server-spec.spawn.test.ts:12-39` voice, stating what the file proves and what it does not — and
carrying the **LLRT vehicle caveat before any result is cited**: this runs under Node, whose
`detached: true` is `setsid()`, while Caido's LLRT is `setpgid(0, 0)`; both yield pgid equal to the
child pid, which is the only property the group-kill argv depends on, so the mechanism transfers — but
the runtime does not, and no CI leg in this repository executes LLRT.

Helpers, all built at runtime with nothing committed (the `spawn-plan.win32.test.ts` convention), under
a `mkdtemp` prefix of `drift-kill-tree-`, with a `tempDirs` array and an `afterEach` that removes them:

- `spawnFixtureTree({ detached })` — writes a parent `.mjs` that spawns a child `.mjs` (both idle for a
  bounded period and then exit on their own, so a failed case leaks nothing), spawns the parent with
  `process.execPath` and the given `detached`, and resolves `{ parentPid, grandchildPid }` from the
  parent's first stdout line.
- `isAlive(pid)` — a positive-pid signal-`0` liveness probe wrapped in `try`/`catch`.
- `settle()` — a bounded wait long enough for a signal to be delivered and reaped.

Two cases, and the control comes first because it is what makes the second one mean anything:

- `"CONTROL: without detached, a single-pid kill leaves the grandchild alive"` — spawn the fixture with
  `detached: false`, kill the parent by its own pid, settle, and assert the grandchild is **still
  alive**. Comment it as the falsifying partner: if this ever goes green by the grandchild dying anyway,
  the premise of LIF-02 is wrong and the next case proves nothing. Record that it was measured on darwin
  on 2026-08-24 and the grandchild survived.
- `"with detached + the plan's group kill, the grandchild dies with the parent"` — spawn with
  `detached: shouldDetachProviderSpawn("linux")`, build the argv by **calling `buildKillTreePlan`**,
  assert `plan.kind` is `"spawn"`, spawn `plan.file` with `plan.args`, settle, and assert both the
  parent and the grandchild are dead. Never write the argv out by hand in this file — a locally
  re-derived argv makes the test agree with itself instead of with production, the rule
  `mcp-server-spec.spawn.test.ts:12-19` states.

Pass a per-`it` timeout as the third argument to `it(...)`, from a single shared constant, so a future
raise cannot apply to only one case.
