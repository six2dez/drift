   no direct MCP call of its own in flight. That gate is what makes it safe, and it covers

## Why Drift's own MCP process needs an exclusion, and why it is a depth counter

`callMcpMethod` spawns `node <mcpTempDir>/mcp-server.mjs` directly for the MCP self-test.
Its argv is byte-identical to the CLI's child, so the scan pattern selects it too. At
teardown that is correct — everything must die. At the *idle* reap it is not: a
concurrently-running self-test would be killed and surface to the user as a self-test
failure with no visible cause.

A pid exclusion list was rejected: a stale pid in such a list would shield a genuine orphan
that later reused the number, which is threat T-08-04's failure shape pointed the wrong
way. A depth COUNTER cannot go stale in that direction. It is incremented once immediately
after the direct spawn and released exactly once — from a guarded release helper called by
both the `close` and the `error` handler — so the arithmetic has one site in each
direction. If the release never runs (Caido's runtime does not reliably deliver
child_process callbacks while an RPC is awaiting), the depth stays positive and the idle
reap is SUPPRESSED. That is the safe direction: every unknown in this phase resolves toward
not killing, exactly as `hasTrackedProcessExited` and `isPidAlive` already do.
