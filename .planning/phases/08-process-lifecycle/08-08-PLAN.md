<objective>
Close **G-01**: on a real install, `killTree` resolves `taskkill.exe` by BARE NAME, which is
the insecure form ROADMAP SC-1 was amended (WR-04) to permit only as a last resort and which
threat **T-08-03** exists to prevent.

The mechanism is measured, not suspected. `readParentEnv()` (`index.ts:573`) reads
`processRef.process?.env` from Caido's plugin sandbox, and the 2026-08-27 diagnostics
reported `parentEnvKeyCount: 0`. `buildKillTreePlan`'s win32 arm scans that record for
`SystemRoot` then `SYSTEMROOT`, finds neither, sets `root === ""` and returns
`DEFAULT_TASKKILL`. Windows resolves a bare name through a search order that includes the
working directory the plugin host chose.

The reading is darwin, where the POSIX arm never consults `root`, so nothing is broken on
macOS today. What makes it a shipping-path defect rather than a remote contingency is the
corroboration: `process.kill`, `process.version` and `process.versions` are ALSO absent from
the same shim. Four absences are a sandbox POLICY, not a host quirk, and a policy is very
unlikely to differ by platform. The bare-name fallback is therefore the EXPECTED Windows
path, not the exceptional one — while every CI leg stays green, because Node populates
`process.env`.

## The scope decision, stated explicitly

G-01's `missing` list asks whether every other `readParentEnv()` consumer inherits the
emptiness. They all do. The line is drawn on **outcome**, not on phase ownership:

**IN SCOPE — three consumers, because each one's empty-environment outcome is a BARE
EXECUTABLE NAME resolved through Windows' search order (the T-08-03 spoofing mechanism):**

| Consumer | Binary | Origin | Why it is here |
|---|---|---|---|
| `buildKillTreePlan` win32 arm | `taskkill.exe` | Phase 8 | The reported gap. |
| `getWhichCommand` win32 arm | `where.exe` | Phase 6 | Identical ladder, identical fallback, same file, reached from `resolveCommand` on every provider status check. |
| `selectComspec` | `cmd.exe` | Phase 7 (CR-01) | Different variable (`COMSPEC`), same emptiness, same outcome — and it is the branch that carries a live Caido session token into a spawn, so it is the most severe of the three. Fixing Phase 8's arm and leaving this one is half a fix. |

All three are ONE root cause and take ONE fix: a Windows system root that does not come
from `process.env`. Building three separate answers would be the expansion-without-bound the
gap warns against; building one and applying it three times is the same work.

**OUT OF SCOPE — recorded as residuals by plan 08-10, with owners, not silently dropped:**

- `getWindowsNamedRoots` and `isNvmWindowsInstalled` (`index.ts:1672-1676`, `:2731-2740`).
  Their empty-environment outcome is FEWER absolute candidate paths for command resolution,
  never a bare name executed. That is a functionality degradation — a Windows user with nvm
  or fnm may be told a command is unresolvable — not a spoofing surface. Owner: Phase 10
  (Windows Polish / not-on-PATH detection), which already owns that user-visible symptom.
- `buildSpawnEnv({ parentEnv })` (`index.ts:653`, `:2079`, `:3203`, `:4405`). Its
  empty-environment outcome is a spawned child receiving only Drift's own variables. No
  bare name is resolved and no search order is consulted. It is a behavioural question that
  needs a real `windows-latest` reading rather than a code change, and today it demonstrably
  works on macOS (18 tools registered, `authState: valid`, on the same install that reported
  the empty environment). Owner: Phase 9, where the first Windows leg runs.

## The non-environment source, and the honesty about it

`os.tmpdir()` is CONFIRMED working on a real Caido install (the same 2026-08-27 diagnostics:
`runtimeOsPlatform: ok (gating)`, `mcpTempDir` correctly resolved beneath it). It is the only
non-`process.env` source of a Windows path this runtime offers. On Windows it returns a
drive-qualified path, so the drive letter is readable and `<drive>:\Windows` follows.

This is a derivation, not a measurement, and it is written as one. `TEMP` can be redirected
to a drive other than the one Windows is installed on, in which case the derived root is
wrong. That failure is ACCEPTABLE and the asymmetry is the whole argument: a wrong derived
absolute path makes the spawn fail loudly with a file-not-found error that a diagnostics
report will show, whereas a bare name silently resolves through a search order that includes
the working directory the plugin host chose — on a security tester's machine. A loud wrong
answer beats a silent compromised one. The bare name stays reachable and tested beneath the
derivation, so SC-1's "last resort" clause becomes true rather than merely written.

Purpose: make SC-1's absolute-path guarantee hold on the environment a real Windows install
actually presents, and close the identical Phase 7 hole in the same edit.
Output: two pure functions in `platform.ts`, one required input member on three consumers,
three updated call sites, and a gate that counts them.
