## Enumeration strategy, and what happens when enumeration is unavailable

Read this before writing any code; it is the design decision this plan exists to encode.

**How enumeration is done.** Caido's plugin sandbox exposes no `process.kill`, an empty
`process.env`, and no `process.version`/`process.versions` (four independent readings,
2026-08-27). It does expose `spawn` — every `resolveCommand`, `spawnAndWait` and `killTree`
call in this codebase depends on it. So enumeration is a **spawn of `pgrep`** with `-f`
(match against the full command line) and an extended regular expression carrying **two
anchors and their adjacency**: the `drift-mcp-<token>` directory name, a separator, and
`mcp-server\.mjs`. Verified runnable on darwin 2026-08-27: `pgrep -f -- 'drift-mcp-[0-9a-f]{8,64}/mcp-server\.mjs'`
returns the matching pid and exit 0, returns nothing and exit 1 when no process matches,
and excludes its own pid.

**Why `pgrep` and not `ps`.** `ps -eo pid=,args=` was the obvious first choice and is
rejected: its output on a real desktop is ~1,300 rows, far past `SPAWN_STDOUT_MAX_CHARS`,
and every bounded buffer in this codebase retains either the head or the tail. A truncated
enumeration silently drops rows, and the row it drops is the one we are looking for — a
reaper that reports success while missing the orphan is worse than no reaper. `pgrep`
returns one integer per match, so there is no volume to truncate. The trade is that the
matching moves into `pgrep`'s regex engine rather than into a pure JS parser; the plan
compensates by keeping the PATTERN construction pure and unit-tested, and by proving the
whole path behaviourally in `orphan-reap.posix.test.ts`.

**When enumeration is unavailable or returns nothing.** Four cases, one outcome:
`pgrep` absent (spawn throws synchronously), non-zero exit (including exit 1, "no match"),
the scan timing out, or output that parses to zero pids. All four log one value-free line
and return, killing nothing. The reaper is **strictly additive**: it can only add a kill of
a process proven to be Drift's by two anchors, and it can never remove or weaken a
termination path that ships today. A host with no `pgrep` is exactly as well served as it
is at HEAD.

**What this plan does NOT deliver, stated here so it is not read in later.** win32 gets no
enumerator: `tasklist` does not print command lines, `wmic` is removed from current
Windows, and spawning PowerShell from the plugin is a surface this phase will not open.
`buildSessionOrphanScanPlan` therefore REFUSES on win32 with `reason: "unsupported-platform"`,
and the win32 termination path stays `taskkill /t`, which walks `ParentProcessId` and is
indifferent to process groups — so A6 was never a Windows question. The residual is that a
Windows orphan of the G-04 shape (launched by a CLI instance Drift did not spawn) is not
reachable by this mechanism. Plan 08-10 records it as **AR-04**.
